# 更新候选池规则

这个目录用于保存尚未进入开发的玩法、美术、技术和体验建议。记录建议不代表已批准、已排期或已实现。

## 默认工作方式

1. 用户提出的新建议默认只登记，不立即修改游戏代码或构建。
2. 登记时补充目的、玩家价值、风险、依赖关系和最小验证方式；信息不足可以保留为待澄清。
3. 小建议先积累到候选池，不为单个小改动频繁发布版本。
4. 当候选内容形成一个目标一致、可测试的版本包时，Codex 主动提示“可以准备下一个版本”，列出范围、暂缓项和风险。
5. 只有用户明确批准该版本包开始开发后，候选项才进入 `NEXT_TASKS.md` 并允许实施。
6. 紧急编译错误、数据损坏风险或阻断测试的问题不作为普通功能建议处理；先说明问题，再取得必要授权处理。

## 候选状态

- `INBOX`：已记录，尚未评估。
- `NEEDS_DESIGN`：方向成立，但规则、交互或平衡仍需设计。
- `READY_FOR_BATCH`：边界、依赖和验收方式已经明确，可被纳入候选版本。
- `PROPOSED_VERSION`：已组成版本包，等待用户批准。
- `APPROVED`：用户已批准，可以转入执行任务。
- `DEFERRED`：有价值，但当前阶段不合适。
- `REJECTED`：经讨论决定不做，并保留理由避免重复评估。

## 何时提示可以更新

不单纯按建议数量判断。一个候选版本至少需要：

- 一个清晰的版本主题；
- 一项主要玩家价值，以及必要的配套小改动；
- 不与当前核心玩法验证目标冲突；
- 已知主要依赖、风险与不做的边界；
- 可在一次版本测试中判断成败的验收条件。

满足这些条件后再建议合并开发，避免功能堆积和反复返工。

## 文件

- `CANDIDATES.md`：所有未实施建议及其状态。
- 未来形成明确版本包时，新建 `VERSION_0_X.md`，经批准后再进入项目执行清单。
